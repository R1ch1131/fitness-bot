# Уведомления FitPulse на iPhone

## Включение на телефоне

1. Нужна iOS 16.4 или новее и HTTPS-адрес приложения.
2. В Safari: «Поделиться» → «На экран “Домой”».
3. Открыть FitPulse с появившегося значка, нажать колокольчик → «Включить» → «Разрешить».
4. Статус «Уведомления подключены» означает, что браузерная подписка сохранена сервером. Нажать «Тест»: сервер отправит настоящий Web Push только на это устройство. Тест не меняет текущий опрос после тренировки.
5. Успешный ответ push-сервиса подтверждает приём, но не показ на телефоне. Проверить Центр уведомлений и настройки «Фокусирования». Для проверки в фоне закрыть приложение и дождаться очередного напоминания.

При запрете уведомлений разрешение меняется в настройках iPhone для установленного приложения. Для отключения одного устройства использовать колокольчик → «Отключить».

### Проверка после 30 минут без приложения

Колокольчик → «Когда отправить тест» → «Через 35 минут» → «Тест». Убедиться, что появилось подтверждение сохранения на сервере, затем закрыть приложение. Доступен также тест через 1 минуту и немедленный тест. Отложенный тест отправляется только на это устройство; повторное планирование заменяет предыдущий тест. Можно отменить его, а при следующем открытии приложение запрашивает сохранённое задание.

Задание хранится в `fitpulse_push_test_queue` в Upstash и локально в `data/push_test_queue.json`. Для сохранения между перезапусками Render нужен настроенный Upstash или постоянный диск. Выполнение проверяется сервером каждые 20 секунд. Если сервер был временно недоступен, тест может прийти позже; через час после запланированного времени невыполненный тест удаляется. Повторные попытки при отказе push-сервиса не подтверждают показ уведомления на телефоне. Отложенные тесты не меняют реальный опрос после тренировки.

Это именно проверка доставки, а не уведомление о начале тренировки. В текущей официальной схеме Hevy API нет документированного события старта или запроса активной незавершённой тренировки. `start_time` в сохранённой записи — время начала в журнале, а не событие в момент нажатия «Начать». Текущий монитор раз в 90 секунд проверяет новые записи и назначает опрос по `end_time`; отсутствие `end_time` не подменяется временем начала. Источник: https://api.hevyapp.com/docs/

## Что отправляется

Все часы указаны в часовом поясе проекта UTC+6 (Омск):

Это расписание по умолчанию. Колокольчик → «Расписание уведомлений»: включить/отключить каждый тип, изменить время и задержку опроса после тренировки (5–120 минут), затем нажать «Сохранить расписание». Настройки общие для PWA на всех устройствах. Telegram сохраняет прежнее расписание. Настройка расписания сама по себе не выдаёт разрешение iOS: уведомления также нужно включить на устройстве.

Настройки хранятся в Upstash под `fitpulse_notification_settings` (если Redis настроен), с локальной копией в `data/notification_settings.json`. Без Redis или постоянного диска локальные настройки могут потеряться при перезапуске Render. Применяются без перезапуска сервера: планировщик проверяет расписание каждые 20 секунд; опрос после тренировки — каждые 15 секунд, плюс задержка обнаружения Hevy. Успешно принятые push-сервисом напоминания записываются в журнал доставки, чтобы не повторять их после деплоя. Если сервер проснулся менее чем через 5 минут после времени напоминания, он попробует отправить пропущенное; более старые напоминания пропускаются. Если уведомление уже отправлено сегодня, изменение его времени не вызовет повторную отправку в тот же день.

| Событие | Время | Переход |
| --- | --- | --- |
| Опрос после тренировки из Hevy | Через 20 минут после окончания, с задержкой опроса Hevy/диспетчера | AI-тренер |
| Сменные вещи в зал | Пн–Пт, 08:30 | Зал |
| Стирка спортивных вещей | Каждый день, 22:00 | Обзор |
| Проверка питания | Каждый день, 23:00 | Обзор |
| Недельные итоги | Вс, 12:00 | Неделя |

Web Push работает при закрытом приложении. Таймеры страницы и периодический fetch сами по себе этого не обеспечивают. Фоновую отправку выполняет сервер.

## Сервер и развёртывание

1. Установить зависимости: `pip install -r requirements.txt`.
2. Собрать клиент: `cd frontend`, `npm ci`, `npm run build`.
3. Запускать `python bot.py` (как в Procfile): именно он запускает планировщики и веб-сервер. Для существующего запуска нужен `TELEGRAM_TOKEN`, даже если пользователь получает сообщения только через PWA. Один `uvicorn api:app` планировщики не запускает.
4. Использовать один постоянно работающий экземпляр. Спящий бесплатный хостинг, перезапуски и несколько реплик не обеспечивают точное расписание: планировщики пока работают в потоках процесса, без отдельной надёжной очереди. Нужен тариф без засыпания для регулярных напоминаний. Самопинг из спящего процесса не поможет.
5. Для постоянных подписок настроить `UPSTASH_REDIS_REST_URL` и `UPSTASH_REDIS_REST_TOKEN` либо постоянный диск для `data/`. При настроенном Redis ошибка сохранения теперь не выдаётся за успешную подписку. Пустой список Redis больше не восстанавливает удалённые подписки с локального диска.
6. Установить новый секрет `VAPID_PRIVATE_KEY_PEM` в настройках сервиса. Поддерживаются настоящий многострочный PEM и строки с `\n`. Публичная часть вычисляется автоматически. Не менять этот секрет при каждом деплое. Опционально `VAPID_SUBJECT=mailto:ваш-реальный-email`.
7. Разрешить исходящий HTTPS к push-провайдерам, включая `*.push.apple.com`. Клиенту нужны доступные с того же origin `/sw.js`, `/manifest.json` и `/api/notifications/*`.

### Замена опубликованного ключа

В исходном репозитории приватная часть VAPID была опубликована в `vapid_keys.json`. Файл удалён из текущего дерева и добавлен в gitignore, но остаётся в старой истории Git. Ключ считать скомпрометированным.

Сгенерировать новую пару локально, например `vapid --gen --applicationServerKey`, и перенести содержимое полученного `private_key.pem` в секрет `VAPID_PRIVATE_KEY_PEM` сервиса. Не коммитить полученные файлы. Для стабильного fallback генерации используется `data/vapid_keys.json`, а не старый файл из корня.

После замены ключа перезапустить сервер и на каждом устройстве снова нажать «Включить». Клиент обнаружит несовпадение ключа и обновит подписку по нажатию пользователя. Существующий ключ в Redis не заменяется автоматически: секрет окружения имеет приоритет.

## Проверки

`python -m unittest test_push -v` — криптография, постоянство ключей, сохранение подписки, целевая доставка, очистка 410, независимость Telegram/PWA.

В `frontend/`: `npm test`, `npm run build`, `npm run lint`. Тесты не отправляют реальные push, не подключаются к Hevy/Telegram/Redis и не проверяют физический iPhone.

Официальная документация: https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/
