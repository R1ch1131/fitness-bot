# Экран пробуждения Render

`APPLICATION LOADING / SERVICE WAKING UP` — служебная страница Render, показанная до запуска веб-приложения. По скриншоту нельзя определить, было ли причиной усыпление, перезапуск или деплой: нужны Events и журналы самого Render.

В предыдущих изменениях ускорения загрузки пинг не менялся: он оставался раз в 10 минут. Но сохранялись только ответы API, а интерфейс каждый раз требовал загрузки с хостинга. Поэтому сохранение данных не защищало от экрана пробуждения.

## Что изменено

- Production-сборка включает в service worker HTML именно этой версии и список её статических ресурсов. После успешного первого открытия интерфейс и ресурсы сохраняются на устройстве.
- Повторное открытие установленного приложения использует сохранённый интерфейс. API и изменения данных никогда не кешируются service worker.
- Страница Render не принимается за ресурс приложения. Неудачная установка новой версии не заменяет работающий service worker; сохранена предыдущая версия ресурсов для уже открытых вкладок.
- Service worker устанавливается независимо от разрешения push. После готовности сервера приложение проверяет обновление service worker.
- Отдельная проверка `/health` отличает JSON приложения от HTML пробуждения, показывает состояние подключения и повторяет попытки. После восстановления связи запрашиваются свежие данные без ручного перезапуска. Пока связи нет, поля и кнопки изменения данных в основном содержимом недоступны.
- Веб-сервер запускается до первоначальной тяжёлой синхронизации Hevy/YAZIO. Встроенный пинг изменён с 10 на 5 минут и обращается к `/health`.

## Что нужно на Render

После деплоя один раз открыть приложение при доступном сервере, чтобы новая версия сохранила интерфейс на устройстве. При первом посещении, удалении кеша или выгрузке кеша системой экран Render всё ещё возможен.

Код страницы не отменяет усыпление/перезапуски хостинга. Встроенный пинг не выполняется, пока процесс остановлен. Проверить существующий внешний монитор: GET `https://fitness-bot-9f8m.onrender.com/health` раз в 5 минут, успешный ответ — JSON с `status: ok`. Проверить историю сбоев монитора и Events в Render за время скриншота. Для гарантии отсутствия автоматического усыпления нужен сервис без такого ограничения.

Пока сервер остановлен, фоновые планировщики не отправляют push, даже если сохранённый интерфейс открывается. Это не заменяет постоянно работающий сервер.

Документация Render: https://render.com/docs/free и https://render.com/docs/troubleshooting-deploys

## Проверки

`npm test` — кеш интерфейса/ресурсов, отказ кеширования HTML Render, отсутствие кеширования API/мутаций, восстановление соединения и прежние функции.

`python -m unittest test_push test_dashboard_loading test_notification_settings test_cold_start -v` — серверные регрессии, в том числе порядок старта и интервал пинга.

Отдельно выполнен браузерный сценарий на production-сборке с тестовыми API: установка service worker → отключение сети → повторное открытие с сохранёнными отметками → имитация HTML Render → восстановление API и редактирования без перезагрузки. Физический iPhone не проверялся.
